## Before the demo — the demo APK, the network, and the laptop (FE-D5)

The demo runs a **release** APK, not a dev build: no Metro, no dev menu, no LogBox. It talks to
the local Supabase stack and the mock **on the laptop**, over plain http, at the laptop's Wi-Fi
address. No credentials appear in this document. The fixture account is printed by the seed (§3),
in the terminal only.

### 0. First, test the network from the phone's browser — before any build

With Supabase and the mock running and exposed (§3), and the phone on the demo Wi-Fi, open these
in the **phone's browser**:

- `http://<DEMO_IP>:54321/auth/v1/health`: any answer (it gives 200, even without a key)
- `http://<DEMO_IP>:4010/visits`: any answer

**Why this comes first:** the address is baked into the APK (§2), and a build takes about ten
minutes. If the phone cannot reach the laptop, because of client isolation, the firewall, or the
wrong network, no build will fix it, and every build before this test is wasted. The laptop cannot
run this test for you: its calls to its own address never cross the firewall. The operator ran
this test on 28 September against `192.168.1.15`, and both answered.

### 1. The network

- **Use the Wi-Fi network the APK was built on:** the laptop's **Wi-Fi** adapter, network
  "NexGen PSPPL 5G", with the laptop at **`192.168.1.15`** (measured 28 September). The phone must
  join **the same network**. The laptop's hotspot adapters were not active, and nothing was built
  for them.
- **Why this one:** it is the network the operator chose and the one that was live when the APK
  was built, and the APK can only reach the address it was built with (§2).
- **Risk to check on the day:** some guest or corporate Wi-Fi networks isolate clients, so devices
  cannot reach each other. If the phone cannot reach the laptop (§3's checks, run *from the
  phone's browser*), that is the likely cause, and changing network means rebuilding (§2).

### 2. The address baked into the APK — rebuild if it changes

The demo APK has these **built in** at build time. They cannot be changed on the phone:

| What | Value |
| --- | --- |
| Supabase | `http://192.168.1.15:54321` |
| API (mock) | `http://192.168.1.15:4010` |
| The only host plain http may reach (`DEMO_CLEARTEXT_HOSTS`) | `192.168.1.15` |
| Name on the home screen | "Field Force (demo)" |

**If the laptop's address changes, the APK must be rebuilt: run the script with the new IP
(§5a)**. It sets all three. This happens on a different network, or if the router hands out a new DHCP lease. A
DHCP reservation for the laptop on the demo network avoids the surprise. Every other host stays
blocked for plain http, by design.

### 3. Start Supabase and the mock, and check each at the LAN address

1. **Docker Desktop** running.
2. **Supabase:** from `services/api`, run `pnpm exec supabase start`. Its API is published on all
   interfaces (`0.0.0.0:54321`), so the LAN address works as it is.
   - Check: `curl http://192.168.1.15:54321/auth/v1/health` → **200** (no key needed for the health
     endpoint).
3. **Re-seed the demo day on Thursday, after 05:30 IST.** The command, from the repo root:

   ```
   pnpm --filter @fieldforce/api run seed:day -- --another
   ```

   - **Why after 05:30 IST:** the seed dates the beat plan with the database's `current_date`, which
     is **UTC**. Run earlier, it would date the plan 30 September.
   - **Why `--another`:** a second plain run **refuses** ("seed:day has already run against this
     database", `seed-day.mjs:196-226`), because a seed ran on 28 September. `--another` adds a
     second demo organisation, on purpose, and destroys nothing. The only other way out the script
     offers is `pnpm db:reset` first, which **deletes the local database** and needs the
     operator's explicit approval.
   - **Each run creates a NEW MR account with new credentials** (new email and password,
     `seed-day.mjs:182-183`). **Sign in on the phone with the account Thursday's run prints**, not
     an older one. An older account still exists but carries 28 September's plan.
   - **After Thursday's re-seed, on the phone (FE-D9):**
     1. **Uninstall the app:** `adb uninstall com.praversetech.fieldforce`, or long-press → Uninstall.
        This deletes the phone's local data, including anything still in its offline queue, so
        first open the queue screen and confirm "Everything is sent".
     2. **Install the latest demo APK** from `C:\dev\demo-apk` (§6): the newest
        `field-force-demo-<ip>-<date>-<commit>.apk`, built by the script (§5a) at the current IP.
     3. **Sign in with the new account** Thursday's run printed.
   - The seed refuses any non-localhost database. It prints the account in the terminal; keep it
     there, never in a file in the repo.
4. **The mock:** `pnpm --filter @fieldforce/mock run build`, then `node services/mock/dist/index.js`.
   - **It listens on `127.0.0.1` only.** That is hard-coded in `services/mock/src/server.ts:1028`,
     and there is no flag, so the phone cannot reach it as it is.
   - Only **Day end** reads the mock (SAMPLE DATA). Every other screen on the path works without it.
   - **Set up the mock for the phone: two commands, in an Administrator terminal.** Replace
     `<DEMO_IP>` with the laptop's address:

     ```
     netsh interface portproxy add v4tov4 listenaddress=<DEMO_IP> listenport=4010 connectaddress=127.0.0.1 connectport=4010
     netsh advfirewall firewall add rule name="Elmiron demo mock 4010" dir=in action=allow protocol=TCP localport=4010 localip=<DEMO_IP> profile=public
     ```

     Check: `curl http://<DEMO_IP>:4010/visits` → **200**, then from the phone's browser (§0).
   - **Remove both after the demo: two commands, in an Administrator terminal:**

     ```
     netsh interface portproxy delete v4tov4 listenaddress=<DEMO_IP> listenport=4010
     netsh advfirewall firewall delete rule name="Elmiron demo mock 4010"
     ```

5. **Local Supabase uses well-known default keys, and it is reachable on the network while it
   runs.** Its API is published on all interfaces, and the local stack's keys are the Supabase
   CLI's public defaults, not secrets. Anyone on the same Wi-Fi who knows them can reach it.
   **Load only fixture data into it** (the seed's synthetic demo organisation), never real doctor or
   rep data. Stop it (`pnpm exec supabase stop` in `services/api`) when the demo is over.

### 4. Windows Firewall

The Wi-Fi network is on the **Public** profile.

- **Supabase (54321):** allowed already. Docker Desktop's own inbound rule ("Docker Desktop
  Backend", Public, TCP, any port) covers the process that publishes it.
- **The mock through the port proxy (4010):** needs its own rule. The proxy listens as a Windows
  service, not as `node.exe`, so the Node.js rule does not cover it. It is the second of the two
  set-up commands in §3.4, and its removal is in the same place.
- **The proof is from the phone,** not the laptop: calls from the laptop to its own address do not
  cross the firewall. Open `http://192.168.1.15:54321/auth/v1/health` in the phone's browser; it
  answers **200 even without a key** (measured 28 September). Any answer means the phone got
  through. The phone's browser may not open plain http without a warning; that is the browser's
  rule, not the app's.

### 5. Keep the laptop awake, with both services running

- Plugged in, with sleep off while plugged in: `powercfg /change standby-timeout-ac 0`. Restore
  your usual value afterwards.
- Lid open, or "When I close the lid: Do nothing" on AC.
- Leave both terminals open: the Supabase stack (in Docker) and the mock. A sleeping laptop, or a
  closed mock terminal, reads on the phone as the request hanging.

### 5a. Building the demo APK — one script (FE-D8)

**If the laptop's IP changes, run the script with the new IP.** Nothing else in the build is done
by hand any more. `apps/field/scripts/build-demo-apk.ps1` does all of it:

- the clean prebuild;
- the cleartext host;
- the CMake 3.31.6 pin;
- the forced JS-bundle rebuild;
- the checks on the finished APK;
- the copy.

The pin still needs CMake 3.31.6 installed, which it was on 28 September (`docs/gotchas.md`).

1. **Commit everything,** so the tree is clean. Supabase must be running (§3).
2. **Set the values the script cannot work out,** in a PowerShell terminal at the repo root. They
   are not secrets; `.env.example` has them:

   ```powershell
   $env:EXPO_PUBLIC_APP_JWT_AUDIENCE = 'authenticated'
   $env:EXPO_PUBLIC_APP_SITE_URL = 'http://127.0.0.1:3000'
   $env:EXPO_PUBLIC_APP_DEEP_LINK_SCHEME = 'com.praversetech.fieldforce'
   $env:EXPO_PUBLIC_APP_ADDITIONAL_REDIRECT_URLS = 'com.praversetech.fieldforce://auth-callback'
   ```

3. **Check first, then build:**

   ```powershell
   powershell -ExecutionPolicy Bypass -File apps\field\scripts\build-demo-apk.ps1 -Ip <DEMO_IP> -CheckOnly
   powershell -ExecutionPolicy Bypass -File apps\field\scripts\build-demo-apk.ps1 -Ip <DEMO_IP>
   ```

   - The build takes about ten minutes.
   - It ends by printing the APK's path, its size and the commit it was built from. The APK lands
     in `C:\dev\demo-apk\` as `field-force-demo-<ip>-<date>-<commit>.apk`.
   - It never overwrites a file there.

The script works out the rest itself:

- it sets the Supabase and API addresses from `-Ip`;
- it reads the Supabase key from `supabase status` into its own environment. The key is never
  printed or written to a file.

**What each refusal means.** The script names every problem it finds, builds nothing, and changes
nothing:

| It says | What it means | What to do |
| --- | --- | --- |
| `<ip> is not assigned to an active network adapter` | That is not this laptop's address on a connected network | Run `ipconfig`, and use the Wi-Fi adapter's IPv4 address |
| `the working tree is not clean` | The APK would not trace to a commit | Commit, or move the listed files out of the repo |
| `Expo reads these ignored files` | An `apps\field\.env*` file would go into the build without being in any commit | Move it out of `apps\field` |
| `local Supabase does not answer` | The app could not sign in | Start Supabase (§3.2) and check the address |
| `supabase status gave no PUBLISHABLE_KEY` | The stack is not running | Start it (§3.2) |
| `EXPO_PUBLIC_APP_… is missing or empty` / `is not a valid …` | A release build without it closes on launch | Set it (step 2) |
| `EXPO_PUBLIC_COACHING_ENABLED is set` / `…RECORDING_ENABLED is set` | Coaching must stay hidden and recording off (§7, P4, P6) | `Remove-Item Env:<name>` |
| **WARNING** `the mock does not answer` | Not a refusal. Only Day end needs the mock, and the build goes ahead | Before the demo, start the mock and set up the port proxy (§3.4) |

If the build itself fails after the checks, the script prints the end of the log and says where the
full log is. The release build is signed with the **debug key** only. There is no real keystore.

### 6. Install the APK

- `adb install -r <path to the demo APK>`.
- **If it fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`**, a dev-client build with the same
  package (`com.praversetech.fieldforce`) is installed and signed differently. Uninstall it first:
  `adb uninstall com.praversetech.fieldforce`.
  - **This deletes that install's local data, including anything still in its offline queue.** Open
    its queue screen first and confirm "Everything is sent".
- A fresh install shows first run, and A4 before the first visit (P5).

### 7. Coaching is hidden in this build, and must stay hidden

Coaching, Analysis and Reply are hidden (FE-D4 1), because their content is mock AI output that
nothing real produces. **Never set `EXPO_PUBLIC_COACHING_ENABLED` for a demo build** (P6). If a
Coaching tab appears on the phone, the wrong APK is installed. The tab bar should show **Today,
Doctors and Me**, and nothing else.

### 8. If demoing on the emulator (FE-D12)

The emulator has no position of its own. Check-in and check-out time out after 10 s ("The phone
could not find your position in time") unless something gives it one. `adb emu geo fix` does not:
it answers OK and the app never receives it (FE-D10).

1. In a terminal at the repo root, **before** pressing check-in:

   ```
   powershell -ExecutionPolicy Bypass -File apps\field\scripts\demo-emulator-location.ps1
   ```

   - It places the emulator at the seeded clinic, **18.5204, 73.8567**. Another point:
     `-Lat <latitude> -Lon <longitude>`, latitude first.
   - It refuses to run unless **exactly one** adb device is attached and its serial starts with
     `emulator-`. **It never touches a real phone.** With a phone plugged in as well, it refuses.
     Unplug the phone, or do not use the script.
   - It prints `Pushing … every second. Press Ctrl+C to stop.` Leave that terminal running for the
     whole walkthrough. Check-out needs a fix too.
2. **Say it out loud:** *"This is the emulator; on a real phone the location comes from the
   device."*
3. Stop it with **Ctrl+C** when the demo is over. It removes nothing. The mock-location setting
   and the test providers stay until the emulator restarts.

At the seeded point, the check-in is recorded `inside` the geofence. That is true of the emulator's
mock position and says nothing about the room. **On a real phone, never use this or any
mock-location app** (see "Check-in indoors, away from the seeded clinic" below).

## Check-in indoors, away from the seeded clinic (FE-D11)

Read from the code on 29 September; nothing was changed. **No option is chosen here. The
operator decides.**

**Where the clinics are.** All three seeded clinics are at one point, **18.5204, 73.8567** (central
Pune), with the default geofence of **150 m** (`services/api/scripts/seed-day.mjs:343`;
`record_check_in`'s `coalesce(geofence_radius_metres, 150)`). A demo room more than 150 m from that
point is "outside" for every visit.

### What the rep sees

| Case | What happens | On screen |
| --- | --- | --- |
| **No fix within 10 s** (`FIX_TIMEOUT_MS = 10_000`, `apps/field/src/capture/location.ts:42`) | Nothing is sent or queued | An amber (`attention`) banner: **"This check-in cannot be sent yet"**, with **"The phone could not find your position in time. Move somewhere with a clearer view of the sky and press again."** The button "I am here — check in" stays. **Pressing it again retries**, with another 10 s |
| **A fix, but far from the clinic** (say 5 km) | **Accepted.** The server records `geofence_status = 'outside'` and the distance | **Exactly the same as an on-site check-in:** "You are checked in", "Checked in HH:MM". No word, colour or icon says "off-site" |
| A fix, within 150 m | Accepted, `inside` | The same as above |
| Outside the working hours | Refused, `45003` | Red (`critical`) "That was refused". The seed's hours are 04:00–23:59 IST, every day, so this should not happen on Thursday |

**Indoors, a fix is likely.** The app asks for `Accuracy.Balanced`, which is Android's fused
`PRIORITY_BALANCED_POWER_ACCURACY`. That takes a **Wi-Fi or cell position**, not only GPS. It needs
Google location accuracy on, and Wi-Fi on (it need not be connected).

**The accuracy is not used for the decision.** It is recorded (`accuracy_metres`), but the geofence
is judged on the fix's centre point (FE-D3 A2). A 100 m-accurate Wi-Fi fix is judged exactly like a
5 m GPS fix.

### Who sees "off-site" later

- **The data exists:** `check_ins.geofence_status = 'outside'` and `distance_from_clinic_metres`.
- **A manager can read it:** row-level security lets a manager read their reps' check-ins
  (`check_ins` select policy, `visible_user_ids()`).
- **No screen shows it today.** Neither the field app nor the console reads either field. A
  manager would see "off-site" only by querying the database.
- An `outside` check-in still starts the visit. Whether it should is registered as an open product
  question (`20260911000300_check_in_starts_the_visit.sql:108-112`).

### The options for Thursday, and what each costs

1. **Demo check-in as it really behaves, and say so.** Check in from the demo room. It will very
   likely be accepted and look like a normal check-in, while being recorded `outside`.
   - **Cost:** the phone gives no sign it was judged off-site, so the presenter must say it out
     loud, and must not describe check-in as "geofence-verified" on screen.
   - Rehearse in the room: the 10 s timeout is the one visible failure indoors. The remedy is to
     retry, or move nearer a window.
2. **Ask the backend owner whether the seed can take the clinic's coordinates** (for example a
   flag for the demo room's latitude and longitude). The seed script is theirs, and it is not
   edited here.
   - **Cost:** their time before Thursday, and a re-run of the seed, which Thursday needs anyway
     (§3.3).
   - **What it buys:** the recorded row says `inside`, which is true for the demo room. **What it
     does not buy:** the phone looks exactly the same either way.
3. **Show the recorded row on the laptop after the check-in.** A read-only query against the
   **local** database (Supabase Studio or `psql`): `geofence_status` and
   `distance_from_clinic_metres` for the check-in just made.
   - **Cost:** a step off the phone. It needs the laptop screen, and a query prepared in
     advance.
   - **What it buys:** the only way today to show that the server did judge the position. It shows
     `outside` unless option 2 is done too.
4. **Check in before the demo**, somewhere with a good fix, and start the walkthrough from a
   checked-in visit.
   - **Cost:** the live check-in moment is lost. It is still recorded `outside` if that spot is
     more than 150 m from the seeded point.
   - Consent, samples, the voice note and check-out all need a checked-in visit. So **skipping
     check-in entirely is not an option**: it closes most of the path.
5. **Not an honest option, listed so it is not reached for on the day:** a mock-location app or
   developer "mock location" on the demo phone, to place it at the seeded clinic. It fabricates the
   position the product exists to record truthfully, and it is an install on the phone.

## If a step goes wrong on the day

| Symptom | Most likely cause | Not the cause |
| --- | --- | --- |
| "This copy of the app is not set up" at launch | P3: API address unset or loopback in a release build | A crash |
| Sign-in refused | P1 or P2: wrong Supabase address, or no seeded rep | The app's auth code |
| Check-in "refused" | Outside the seeded shift window or geofence (P2) | The queue |
| Report heading "This visit" | The visit is not on the phone yet: the last pull has not brought it (P1, P2) | The mock (the report no longer reads it, FE-D4 2) |
| Day end shows "not available" | The mock is not reachable (P3) | The day's real data |
| The app closes ("keeps stopping") right after **Sign in** | An APK older than FE-D9 (`8607101`): signing out and back in without closing the app crashed every build before it. Install the latest APK (§6). If it happens anyway, reopen the app: the sign-in went through and Home opens | The account or the network |

**Open requests this document depends on:** CR-3 (the mock screens), and the backend owner's answer
on P2 (seed coverage). Neither blocks the REAL screens.
